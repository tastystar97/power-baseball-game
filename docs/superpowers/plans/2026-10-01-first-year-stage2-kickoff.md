## 2. 시작 전 확인

- **단계 1이 완료·병합되었는지** 확인한다. 완료되지 않았으면 시작하지 말고 사용자에게 알린다.
- `git status`가 깨끗한지 확인한다. 아니면 시작하지 말고 알린다.
- 기준 브랜치는 사용자가 지정한 것을 쓴다. 지정이 없으면 단계 1이 병합된 최신 커밋에서 `feature/first-year-stage2`를 만든다.
- 단계 1에서 바뀐 능력 구조(1차 0~1500, 시작값, 카드 학년 항목, 화면 로그, 공용 주사위 컴포넌트)를 코드에서 확인한다. 계획과 다른 점은 "검증 기록"에 남긴다.
- `npm test`, `npm run typecheck`, `npm run build`의 기준 결과를 기록한다.

## 3. 이번 단계의 범위

구현 계획 단계 2의 작업 2.1~2.3이다.

- **2.1** 배경(CYOA) 선택표와 재능 판정 규칙. 예산 10, 약점 최대 2개다. 재능 굴림은 `166 + 2d6 × 12`이고, 주사위 합으로 등급 D~S를 정한다. S는 성장 ×1.15와 상한 +50, D는 성장 ×0.92와 포인트 +2다. 다시 굴리기는 3회이고, 운명 주사위 d20에서 20이면 숨은 재능을 얻는다.
- **2.2** 스카우트 가챠. 중복 없이 10장(넓은 인맥이면 12장)을 뽑는다. 진급 뽑기와 같은 함수를 쓴다.
- **2.3** 7단계 캐릭터 메이킹 화면(이름·역할 → 배경 → 재능 판정 → 운명 주사위 → 스카우트 → 덱 구성 → 스카우트 리포트)과 저장 연결.

## 4. 사용자가 확정한 결정 (이번 단계 관련)

- 캐릭터 메이킹은 **서포트 카드 가챠 + CYOA + 주사위** 방식이다.
- CYOA는 포인트로 출신·체격·성격·특기를 사고, 약점으로 포인트를 버는 선택표다. 효과는 이미 있는 시스템에만 연결한다.
- 주사위는 **이 선수가 어느 정도 재능 있는 선수인지 판별**한다. 등급 차이가 1학년, 특히 6월 선발 경쟁에서 체감되어야 한다.
- 가챠는 지금 **중복 방지만** 한다. 희귀도와 중복 돌파는 카드가 늘어난 뒤에 다룬다. 과금이나 게임 내 재화는 없다.
- 주사위는 확정된 결과를 보여 주는 연출이고, 화면은 계산된 결과만 보여 준다.
- 연애와 관련된 배경이나 효과는 만들지 않는다.

## 5. 작업 방식

- 규칙(배경 검증, 굴림, 등급, 뽑기)은 실패하는 테스트를 먼저 쓴다. 등급 확률은 대량 표본으로 설계 표와 근사하는지 확인한다.
- 배경 선택표와 숨은 재능 목록은 콘텐츠로 둔다.
- 캐릭터 메이킹 도중 새로고침할 때 같은 결과를 유지하는 방법을 정하고 검증 기록에 남긴다.
- 커밋은 기능 브랜치에 작업 단위로 한다. 푸시와 병합은 사용자가 요청할 때만 한다.

## 6. 하지 않을 것

- 7월 이후 일정·캠프·부상·경기 결과 보상(단계 3), 진급 브리지(단계 4).
- 신입생 카드, 희귀도·중복 돌파.
- 배경별 사건 대사의 대량 작성. 이번에는 배경을 저장하고 사건에서 쓸 수 있게만 한다. 예시 사건은 1~2개면 충분하다.

## 7. 완료 기준

- `npm test`, `npm run typecheck`, `npm run build`가 통과한다.
- 브라우저로 다음을 확인한다.
  - 타자·투수를 각각 만들어 3~6월을 진행한다.
  - 7단계 모두를 모바일 폭과 키보드로 조작한다.
  - 배경 변경 시 확인, 다시 굴리기 횟수, 카드 뒤집기와 "모두 뒤집기"가 동작한다.
  - 기존 저장의 덮어쓰기 확인이 동작한다.
  - 캐릭터 메이킹 소요 시간을 잰다(목표 3~5분).
- 실제 규칙으로 재능 등급 D와 S의 6월 선발 점수를 측정하고 설계 표(D 65, S 72~73)와 비교해 기록한다.
- 저장 버전, README, 캐릭터 메이킹 설계의 구현 상태, 구현 계획 체크박스와 검증 기록, `package.json` 버전을 갱신한다.
- 완료 보고에는 다음을 구분해서 적는다.
  - 바꾼 것
  - 검증한 것
  - 남은 제한(배경 수치·숨은 재능·등급 성장률은 플레이 테스트 대상)
  - 검증하지 못한 범위
