# 경기 개편 구현 계획

> **For agentic workers:** Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** 경기 전체를 타석 단위로 시뮬레이션하고 야구장 연출로 재생하다가, 중요 순간마다 멈춰 주인공이 작전을 고르는 약 3분짜리 선택형 경기를 만든다. 타자의 타순 승격과 투수의 보직 선택 서사를 함께 구현한다.

**Architecture:** 게임 규칙이 타석 하나를 4단계로 판정해 `PlayEvent`를 만들고, 같은 이벤트로 주자·점수·기록을 갱신한다. 화면은 저장된 이벤트를 재생만 하고 확률이나 결과를 다시 계산하지 않는다. 선수단은 콘텐츠의 이름·특징과 능력 생성 규칙으로 만든다.

**Tech Stack:** 현재 React·TypeScript·Vite·Zod와 Node 내장 테스트(`npm test`, `npm run typecheck`, `npm run build`). 의존성은 추가하지 않는다. 야구장은 SVG와 CSS 애니메이션으로 그린다.

**Spec:** [경기 개편](../specs/2026-10-01-match-overhaul.md), [경기 선수단](../specs/2026-10-01-match-rosters.md)

## 시작 전 조건

2026-10-01 착수 확인: v0.7 커밋 `e11c5aa`가 원격과 일치하며 깨끗한 상태에서 `feature/match-overhaul`을 만들었다. 기준 테스트 128/128, 타입 검사·빌드 통과. 저장 v7과 기존 3회 선택 제한을 확인했다. 현재 기본 스킬은 44종이며 외부 선언 효과도 있으므로 모두 유지한다. 정태오·서지환에는 기존 숫자 능력이 없어 승인된 선수단 규칙으로 고정 생성한다.

- 이 계획을 쓴 시점에 작업 트리에는 `codex/development-loop-intelligence` 브랜치의 커밋되지 않은 변경(v0.6 스탯 개편, 카드 플랫폼 등)이 많다. 경기 코드(`match.ts`, `types.ts`, `MatchScreen.tsx`)가 겹치므로, **그 작업이 커밋되거나 정리된 뒤 새 브랜치에서 시작한다.** 다른 작업의 변경을 덮어쓰거나 함께 커밋하지 않는다.
- 시작할 때 실제 저장 버전, 경기 스키마, 선발 평가 공식을 다시 읽고 아래 파일명과 인터페이스를 맞춘다. 이 계획은 저장 v7, `match.highlights` 최대 3회, 누적 기반 `candidateScore`를 기준으로 썼다.

## 공통 제약과 구현 판단

- 선택형 경기를 유지한다. 실시간 조작을 넣지 않는다.
- 판정 순서는 승부 결과 → 타구 → 수비 → 주자 진루다. 작전 미리 보기와 실제 판정은 같은 분포 함수를 쓴다. 미리 보기는 난수를 소비하지 않는다.
- 아웃·진루·득점·타점·타수는 `PlayEvent` 하나에서만 계산한다. 화면과 기록이 서로 다른 계산을 하지 않는다.
- 스킬 발동 판정은 v0.6 규칙(지능 기반, 타석당 1회)을 유지한다. 효과의 대상 결과는 새 결과 종류에 맞게 다시 연결한다.
- 연출 시간 표는 콘텐츠 상수 하나로 둔다. 밸런스 테스트와 화면 재생기가 같은 표를 쓴다.
- 재생 속도 설정은 `localStorage`의 화면 설정이며 게임 저장에 넣지 않는다. 접근은 모두 `try/catch`로 감싼다.
- 승리 확률 표시는 보류한다. 강등과 주인공의 도루 선택은 이번 범위가 아니다.

## 중점 검증

- 병살·희생플라이·실책·도루 실패·끝내기·연장 승부치기 주자의 아웃·득점·타점·타수.
- 투수 정지 조건 네 가지의 경계와 조합, 교체 후 선택 없음, 마무리의 모든 타자 정지와 등판 보장.
- 재생 도중이나 선택 지점에서 저장·재개해도 결과와 보상이 바뀌거나 중복되지 않음.
- 1,000경기 시뮬레이션의 득점·안타·병살·홈런 분포, 정지 횟수, 연출 시간 합계.
- 타자·투수 각각 실제 브라우저 한 경기 시간 측정(목표 약 3분), 모바일 폭과 키보드 조작.
